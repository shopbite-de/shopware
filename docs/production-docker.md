# Production Docker Setup

The production build follows the official Shopware hosting guide
(<https://developer.shopware.com/docs/guides/hosting/installation-updates/docker.html>)
and the `shopware/docker` 0.3 Flex recipe.

## Pieces

| File | Purpose |
| --- | --- |
| `docker/Dockerfile` | Two-stage build: `shopware-cli project ci` (composer install, asset build, SBOM) → `docker-base:8.4-frankenphp` |
| `docker/Caddyfile` | Base-image Caddyfile plus `Cache-Control: public, max-age=31536000, immutable` for `/media`, `/thumbnail`, `/bundles`, `/theme` (Lighthouse "efficient cache policy") |
| `.dockerignore` | Keeps `vendor/`, `var/`, `.env.local`, media, `.git` etc. out of the build context |
| `.shopware-project.yml` | Build options for `shopware-cli` and deployment options for the Deployment Helper |
| `compose.prod.yaml` | Self-contained stack: MariaDB, Valkey, `init-perm`, `init` (Deployment Helper), `web`, `worker`, `scheduler` |
| `compose.dokploy.yaml` | Same stack for Dokploy: `expose` instead of `ports`, `web` joined to `dokploy-network` for Traefik |
| `docker/dokploy.env.example` | Variables to paste into the Dokploy "Environment" tab |
| `docker/prod.env.example` | Template for `docker/prod.env` (git-ignored): URL, secrets, DB password, admin user |
| `config/packages/prod/shopware.yaml` | Redis for cache, sessions, carts, number ranges, locks and delayed invalidation |
| `config/packages/prod/monolog.yaml` | JSON logs to stderr, level via `MONOLOG_LOG_LEVEL` |

## First deployment

```bash
cp docker/prod.env.example docker/prod.env
openssl rand -hex 32   # APP_SECRET
openssl rand -hex 32   # INSTANCE_ID
# fill in APP_URL, DB_PASSWORD, DB_ROOT_PASSWORD, INSTALL_ADMIN_PASSWORD, ...

make prod-build        # docker build --pull -f docker/Dockerfile
make prod-up           # starts db + valkey, runs the Deployment Helper, then web/worker/scheduler
make prod-ps
```

The `init` service runs `vendor/bin/shopware-deployment-helper run` on every `up`.
On an empty database it performs `system:install`, creates the admin user from
`INSTALL_ADMIN_*`, creates the Storefront sales channel and installs/activates all
plugins from `composer.json` and `custom/plugins`. On later runs it applies migrations,
updates plugins and compiles the theme. `web`, `worker` and `scheduler` only start once
`init` has exited successfully.

## Updating

```bash
# Shopware / plugin / own code change:
composer update ... && git commit
make prod-deploy       # = prod-build + prod-up

# PHP or OS security fix only (no code change):
make prod-deploy       # --pull fetches the daily rebuilt base image
```

Scan the image regularly (e.g. `trivy image shopbite/shopware:latest`) and rebuild when
findings appear. The SBOM generated by `project ci` is at `/var/www/html/sbom.cdx.json`.

## Build secrets

Both are optional and only used when passed:

```bash
# private composer repositories
docker build --secret id=composer_auth,src=auth.json ...
# packages.shopware.com (Store plugins via composer)
SHOPWARE_PACKAGES_TOKEN=... docker build --secret id=packages_token,env=SHOPWARE_PACKAGES_TOKEN ...
```

`make prod-build` adds them automatically when `auth.json` exists or
`SHOPWARE_PACKAGES_TOKEN` is set (also via `docker/prod.env`).

## Runtime layout

- Shopware runs as `www-data` (uid 82) under FrankenPHP/Caddy on port 8000. Terminate TLS in a reverse proxy and keep `TRUSTED_PROXIES=private_ranges` so `APP_URL`/`https` are detected correctly.
- State lives in named volumes: `db-data`, `valkey-data`, `files`, `media`, `thumbnail`, `theme`, `sitemap`. For multi-host setups move media/files to S3 via `shopware.filesystem` and drop the volumes.
- Valkey uses `volatile-lru`: only keys with a TTL (cache, sessions, locks) are evicted; carts and number ranges are safe. RDB + AOF persistence keeps sessions and carts across restarts. For very large shops split it into an ephemeral (cache) and a persistent (cart/session) instance as recommended in the Shopware Redis guide.
- The message queue stays on Doctrine (`MESSENGER_TRANSPORT_DSN` default). Scale consumers with `WORKER_REPLICAS`.
- Logs go to stderr as JSON: `make prod-logs`.
- Health: `web` reports healthy via `GET /api/_info/health-check`. The base image's own Caddy healthcheck is disabled on `worker`, `scheduler` and `init`, which do not run a web server.
- Shopware Services (Copilot, AI tools, Nexus) are disabled via `ENABLE_SERVICES=0`. Set it to `1` if you want them; registration needs a publicly reachable `APP_URL`.

## Dokploy

Dokploy runs `docker compose -p <app> --env-file .env -f compose.dokploy.yaml up -d --build --remove-orphans`
on every deploy. `compose.dokploy.yaml` is the self-contained stack (MariaDB, Valkey, `init-perm`, `init`,
`web`, `worker`, `scheduler`). Because `init` is a one-shot service that `web`, `worker` and `scheduler`
depend on, every deploy builds the image, runs the Deployment Helper (migrations via
`system:update:finish`, plugin install/update, theme compile) and only then recreates the running containers.

Setup:

1. Create a **Compose** service (not Stack: Swarm cannot `build` and does not support `depends_on` conditions).
   Source: this repository, compose path `./compose.dokploy.yaml`.
2. Environment tab: paste `docker/dokploy.env.example` and fill in `APP_URL`, `APP_SECRET`, `INSTANCE_ID`,
   `DB_PASSWORD`, `DB_ROOT_PASSWORD`, `INSTALL_ADMIN_PASSWORD`, `INSTALL_ADMIN_EMAIL`.
3. Domains tab: add the shop domain, service `web`, container port `8000`, HTTPS on. Dokploy adds the
   Traefik labels itself; `TRUSTED_PROXIES=private_ranges` makes Shopware trust the forwarded `https`.
4. Deploy. Watch the `init` container log for the Deployment Helper output.
5. Enable Dokploy Volume Backups for `db-data` and the file volumes (`files`, `media`, `thumbnail`,
   `theme`, `sitemap`). `valkey-data` only holds sessions and carts.

Networking: MariaDB and Valkey stay on the private project network and are not reachable from other
Dokploy services. `web` is on both the project network and `dokploy-network` (Traefik). Dokploy would
add `dokploy-network` to the domain service anyway; listing it explicitly keeps the project network too.

Downtime per deploy is the container recreation of `web` (a few seconds) after `init` has finished.
